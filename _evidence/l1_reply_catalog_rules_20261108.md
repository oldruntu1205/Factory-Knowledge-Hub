**L1 裁决：有条件通过。选择“缺配置拒绝、应用层校验、方案 A、`text[]`、保留变更审计”。** 本轮不要求触发器或独立货币表，但需要补齐规则变更与并发写入的语义。

1. **新租户无规则：拒绝目录入库。**  
   同意你的倾向。内置工厂默认会把刚移除的隐式业务假设重新带回来。已有租户由迁移显式初始化；新租户在开通目录能力时创建规则，部署或租户初始化流程负责这一步。缺配置应返回可识别的配置错误，不能被当成“文档没有可抽取货号”。已有目录的读取不应因此被禁止。

2. **DB：通用格式约束 + 应用层规则校验，不加触发器。**  
   这是合理的责任边界：DB 保证通用数据形状，应用层保证租户业务规则。前提是**所有目录写入路径共用同一套校验**，包括冲突决议、回填和后台任务；CLI 读取规则仅用于提前报错，最终写入仍须校验。若存在必须支持的直接 SQL 写入方，这个前提就不成立，需要重新评估触发器。

   正则应统一使用一种应用层引擎，并采用**整串匹配**。PUT 的“可编译”校验、入库校验和表格判定必须遵循同一语义；同时限制表达式长度和匹配成本，仅能编译不代表适合执行。

3. **纯函数：接受 A，显式传入规则。**  
   调用点改动属于这次消除硬编码的必要范围。调用方负责加载规则，纯函数负责判定；不要在函数内部查库，也不要保留 B 的隐式默认。建议传入统一的已校验规则对象或匹配器，避免各调用点重复解释 pattern。

   另一个验收点是：**纯数字 EAN 与价格、数量可能重叠**。正则匹配只能说明“可能是货号”，不能单凭它认定货号行；仍需结合既有行列上下文。替换正则本身不足以证明 EAN 场景已经成立，这不要求修改价签解析逻辑。

4. **货币集合：本轮接受 `text[]`。**  
   当前需求只是租户允许集合，独立表没有必要。要求集合非空、不含 NULL、元素唯一且均为三位大写字母；PUT 规范化后保存。这里的三位大写检查仅保证格式，若产品承诺真实货币码，还需明确验证标准，不能把两者等同。

   汇率和小数位是不同职责，未来出现需求时再建模，不必据此提前拆表。

5. **PUT：需要审计，但不强制另建 `catalog_rule_revisions`。**  
   优先复用已有的持久审计机制，记录租户、操作者、时间、变更前后规则及版本，并与更新保持原子性。若现有机制不能提供这些能力，本轮应增加最小审计记录；只有 `updated_at` 不够。相同内容的重复 PUT 应视为无变更，避免制造无意义版本。

通过前还需补充三项设计约定：

- **存量兼容策略：本轮建议拒绝使存量数据失效的 PUT。** 更新后的规则必须覆盖两个表中的现有货号，以及目录中的现有货币。放宽规则通常可以直接成功；收紧规则须先处理不兼容数据。这样可以保持“当前规则适用于当前目录”的清晰语义。
- **并发与在途任务：以最终写入时的规则为准。** PUT 的存量检查、规则更新，以及目录写入，需要按租户协调事务，防止“检查通过后，旧规则任务又写入不兼容数据”。可用规则行锁实现；仅在任务启动时读取规则，或仅增加版本号，都不足以消除竞态。
- **回滚检查必须覆盖两张货号表。** 除 `catalog_items` 外，必须检查 `catalog_conflict_groups.code`，并检查非 CNY 货币；检查与恢复约束应处于同一事务，避免并发写入穿过检查窗口。

另外，当前表结构实际表达的是**每租户规则**。端点应从认证上下文确定租户；若文档继续称“本实例”，需要明确实例与租户的对应关系，避免后续出现两套配置归属解释。
