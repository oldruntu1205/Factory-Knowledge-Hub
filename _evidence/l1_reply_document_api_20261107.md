1. **scope：采用你的倾向。**  
   上传用 `knowledge.ingest`，列表用 `knowledge.read`，审核沿用 `knowledge.review`。明确 `knowledge.read` 是**文档管理元数据读取权限**；这些操作权限与 `required_scope` 的数据范围授权分别校验，彼此不隐含授予。上传权限也不自动包含审核、发布权限。

2. **传输与体积：接受 JSON + base64、解码后 5 MiB、413。**  
   新增唯一错误码 `PAYLOAD_TOO_LARGE`，不复用 422。必须同时限制 HTTP 请求体总大小：5 MiB 原文编码后约 6.67 MiB，另留有界的 JSON 元数据额度，不能先无上限读完整请求再检查。严格校验 base64；非法编码返回 422。体积、格式、字段与权限校验均须在写库前完成。  
   本片同时明确支持的文件格式和字符编码；base64 本身不提供文件解析能力。

3. **重复键：接受 409，但应称为“重复拒绝”。**  
   同租户 `knowledge_key` 重复返回 `409 VERSION_CONFLICT`，不覆盖、不创建新版本。这并不提供“重试返回原成功结果”的幂等保证：首次成功但响应丢失，重试仍会收到 409。唯一性必须由数据库约束或等效的并发安全机制保证，不能只靠写前查询。失败不得遗留文档、版本、切片或目录等部分写入。

4. **列表可见性：接受管理面与冲突接口采用不同规则，但需补齐定义。**  
   可以不做逐块 ACL；前提是将 `knowledge.read` 明确定义为：允许在获授权的数据范围内查看文档管理元数据，包括不可检索状态的版本。该权限不因此授予正文、切片或检索访问权。若 `classification`、`audience` 属于既有硬访问边界，也不能被此接口绕过。  
   查询顺序必须是：**限定租户 → 确定每个文档的最新版本 → 校验其数据范围并应用 status/domain 过滤 → 排序分页**。最新版本不可见或不匹配时，不能退回旧版本。  
   此外，上传时必须校验调用者是否有权指定相应的 `required_scope`、分级、受众和 ACL，不能仅检查其拥有 `knowledge.ingest`。

5. **初始状态：同意固定为 `DRAFT`。**  
   请求不得指定初始状态或跳过审核。检索资格由既有状态机决定；“review→approve”应在文档中对应到明确的动作和目标状态，不能把仅完成 review 写成已经可检索。

6. **命名遗留：本片不改旧路径。**  
   新接口统一返回 `version_id`；旧接口的 OpenAPI 参数说明和调用示例明确“`knowledge_id` 实际接收 `version_id`”。无需顺带改名或新增兼容路径。

7. **目录抽取：保持现行为。**  
   `product_catalog` 上传继续触发抽取及冲突待办。抽取出的条目不得绕过既有审核、发布和可见性规则。明确失败语义：硬失败不能留下部分入库；若既有规则允许抽取失败后保留草稿，须通过 `warnings` 明确返回，不能伪装成完整成功。
