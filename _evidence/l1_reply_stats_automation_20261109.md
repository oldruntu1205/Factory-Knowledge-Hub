VERDICT: PASS

MUST_FIX:
- 无。仅依据本文判断方案成立；不代表已核验代码或复现测试。PASS 的依据是刷新与失效回退机制衔接合理，并非“无 schema 变更”。

SHOULD_FIX:
- 告警接线：结构化 stderr 和非 0 退出满足“可告警”，但不等于告警已送达。补充日志事件的采集方式、触发规则，并做一次故障演练。
- 失败链路证据：补测真实刷新异常后，FAILED/last_error 持久化、后续 tenant 仍成功、watch 返回 1。直接调用 `mark_failed` 不能完整证明这条链路。
- 维护权限：独立维护进程使用管理员连接可接受本阶段接线；常驻生产服务建议改为最小权限维护角色。`BYPASSRLS` 是否必要取决于现有 RLS；无需为此强制引入 SECURITY DEFINER。
- 并发失败标记：独立事务写 FAILED 合理，失败后回退 live 也安全；建议按刷新对应的 revision 或尝试标识更新，避免较旧失败覆盖较新成功状态。
- 重启策略：失败退出、守护重启可以接受；明确退避和重复告警抑制。它并不天然优于循环内重试，关键是失败可见、重试受控。

BOUNDARY:
- 本轮无需改用 LISTEN/NOTIFY、任务队列或进程内后台线程。
- 轮询提供最终刷新；正常刷新延迟还包含轮询等待和 tenant 排队时间。
- 单 tenant 失败后继续处理其他 tenant、整轮结束再退出，符合目标。
- 本次认可的是“异步刷新、失败可见且可接告警”的方案；不宣称实际告警通知已接通。
