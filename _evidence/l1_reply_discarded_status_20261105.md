1. **方案选择 → 采纳 B，新增 `DISCARDED`。**  
   理由：将“未曾公开发布而主动作废”与撤销分开；是否曾公开仍应以完整发布历史为准，不能只看当前状态。  
   **需要的断言：**状态、动作、应用白名单、数据库约束一致；弃用必须原子写入状态、操作审计和 outbox，审计包含操作者、原因、来源状态与时间。

2. **允许的源状态 → 允许 `DRAFT`、`REVIEWED`、`APPROVED_INTERNAL → DISCARDED`；另允许第 3 项的 `RAW`。**  
   理由：这些状态在所列状态机下未曾公开发布；`SUPERSEDED` 可能来自内部批准，不能一概称为曾公开，但统一保留既有撤销路径。  
   **需要的断言：**8×8 应用层与数据库逐对一致；`PUBLISHED_PUBLIC`、`SUPERSEDED`、`REVOKED → DISCARDED` 均拒绝；改写现有“草稿不能撤销”保护用例时，仍保留 `DRAFT → REVOKED` 被拒绝的断言，另验证可弃用。

3. **`RAW` 直接弃用 → 允许。**  
   理由：上传即发现错误时应能立即终止，无须先制造一次草稿流转。  
   **需要的断言：**`RAW → DISCARDED` 成功；与解析、切片任务并发时，后台任务不得将已弃用版本推进为 `DRAFT`，或继续为其提交新切片。

4. **`approved_by` → 保留弃用前已有值，不因弃用清空或补写。**  
   理由：审批是已发生的历史事实，弃用不应抹去；这里的语义应表述为“批准过但未曾公开发布”，因为内部批准版本可能已对内部可见。  
   **需要的断言：**从 `APPROVED_INTERNAL` 弃用后审批人与审批时间不变；其他来源不得借弃用伪造审批信息；弃用操作者独立记录。

5. **新事件 → 新增 `knowledge.version.discarded.v1`，加入封闭 enum。**  
   理由：弃用是独立领域事实，需要明确的对外契约，不能复用撤销事件。  
   **需要的断言：**事件通过 schema 校验，能够标识租户、版本、来源状态及对应审计；一次成功弃用恰好产生一条 outbox 记录，重复请求不重复产生审计或事件；投递重试沿用同一事件标识。此处不承诺消息恰好投递一次。

6. **培训联动 → 要，引用该版本的已发布课程转 `NEEDS_REVIEW`。**  
   理由：内部可用过的内容同样可能被弃用，已发布课程不能继续向学员提供该内容。  
   **需要的断言：**弃用与课程状态变更原子完成；仅影响本租户实际引用该版本的已发布课程；验证学员访问确实被阻断，不能仅检查课程状态字段。

7. **保留期限 → 本轮允许只标记、不物理清理；具体期限「待业务确认」。**  
   理由：提供的材料不足以确定 ADR-05 的具体期限，不能据此裁定立即删除或永久保留。  
   **需要的断言：**本轮不删除版本和切片；常规检索、业务证据端点排除弃用内容，授权审计仍可追溯；后续清理须明确版本、切片、引用与审计各自的保留规则。误传客户资料所需的紧急清理期限另待业务确认。

8. **`version_no` → 不回收、不复用。**  
   理由：版本号承担稳定引用身份，弃用不应让同一编号指向另一份内容。  
   **需要的断言：**弃用后新版本继续递增，原编号仍定位原记录，并发创建也不得复用编号。该方案解决终止问题，不消除编号空档。

9. **`DISCARDED` → 终态，不可复活；恢复内容须建新版本。**  
   理由：终止事实必须稳定，否则审计、事件和课程联动会产生反向语义。  
   **需要的断言：**禁止所有离开 `DISCARDED` 的状态迁移；重复弃用按幂等请求处理，不产生新副作用；内容仍不可变。

10. **审批要求 → 单主体执行，不要求双签。**  
    理由：弃用收回可用性，不授予发布资格，可沿用撤销的授权强度。  
    **需要的断言：**沿用撤销的角色与对象权限规则，不因允许 `RAW/DRAFT` 弃用而自动扩大上传者权限；跨租户返回 403，无权限请求不产生状态、审计、事件或课程变更。

**实施约束：**迁移使用 `0013`，不得回填 `0010`。回滚前必须检查 `DISCARDED` 数据及 `DISCARD` 审计记录；存在时禁止直接收紧约束，也不得自动改写为 `REVOKED`。新增状态与事件属于契约扩展，终审需核对契约版本及兼容性说明。
