# 客户目录评测：#货号/价格类问题是否适合走文本 RAG

- 日期：2026-11-06
- 语料：三爱思 2023 产品目录（88 页；去 3 页无文本页后 **85 页 / 76,854 字符**）
- 派生：`_corpus/`（gitignored，含客户价格，**不进仓库**）；本文只报聚合指标与结论
- 工具：`fkh.tools.recall_benchmark`（既有）+ 答案级评估脚本（临时）

## 1. 语料规模

| 指标 | 数值 |
|---|---|
| 可抽取页 | 85 / 88（第 2、3 页为纯图片） |
| 正文字符 | 76,854 |
| 切片块数 | 196（含 parent/child） |
| 自动识别「货号 → 单价」行 | **1,281 条**（脚本校验整行在语料内唯一） |

## 2. 检索召回（30 条自动生成用例，k=10）

| 模式 | recall@10 | 平均单查耗时 |
|---|---|---|
| 词法（`lexical-v2`，生产默认） | **0 / 30 = 0.00** | 13.0 ms |
| 混合（BGE-M3 + RRF，opt-in） | **2 / 30 = 0.067** | 91.1 ms |

**先排除"切块切坏了"**：逐条核对 10 个用例，每个「货号 + 规格 + 单价」整行都**完整存在**于
2 个块中（parent + child），说明问题**不在切块，而在排序**：

- 词法查询按字切分并 OR 组合，"货号 A282450 的单价是多少" 里的「货」「号」「单」「价」等
  高频字命中大量价格表块，正确块被淹没；
- 向量对"查具体编号"这种精确匹配天然不擅长。

## 3. 答案级（10 条，qwen3:14b，think=false）

| 指标 | 结果 |
|---|---|
| `ANSWERED` | **0 / 10** |
| 答案里出现正确价格 | 3 / 10（C04、C07、C10 数值正确） |
| 带引用 | **0 / 10** |
| 引用指向含该行的块 | 0 / 10 |

两点分开看：

1. **模型不标引用**：即使在答对价格的 3 条里，也没有输出 `[evidence_id]`，按现行严格规则
   全部降级为 `REFUSED + 人工复核`。这是引用协议在 14B 上的真实遵循率（不是解析 bug）。
2. **部分"没找到"是检索没给对块**（同 §2 的排序问题），不是模型瞎说。

## 4. 结论

**价格/货号类问题不适合走文本 RAG，应转结构化通道。** 依据：

- 检索侧：recall@10 ≈ 0，且已排除切块因素，属于"精确匹配"任务被"模糊检索"处理；
- 生成侧：14B 不遵守引用协议，即使在给出正确价格时也不标注来源，导致答案不可信；
- 数据侧：1,281 条「货号 → 规格/单价」是**确定性对应**，可以机器校验、不需要模型。

拟议做法（下一步切片）：

1. 迁移新增目录条目表（货号、规格、单价、来源 version/chunk/locator、租户）；
2. 入库时从"货号 … 单价"行抽取，作为**可校验的结构化事实**（不是模型生成）；
3. 问答路由：识别到货号/报价类意图 → 走精确查询，直接返回条目 + 原文定位（不经模型）；
   其余描述类问题仍走 RAG；
4. 结构化结果同样落 `rag_queries`/`rag_citations` 审计，保持可追溯。

## 5. 这份语料仍然值得用

- 它自带 1,281 条 ground truth，是**很好的验收语料**：可以同时量"结构化通道准确率"与
  "RAG 在描述类问题上的表现"（如"哪一款适合做回流提取"）。
- 也暴露了当前 RAG 的真实短板：精确编号、长表格、报价，这类问题不能靠模型硬读。
