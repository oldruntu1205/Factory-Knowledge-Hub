**裁决：本片业务实施通过；对外交付前必须补齐实际请求体的硬上限。** 以下判断仅依据送审材料，未探索仓库、读取源码或运行测试。

1. **七条落实：第 1、3—7 条满足；第 2 条仍有缺口。**

   scope 分离、数据库唯一约束、失败原子性、先取最新版再判断可见性、固定 `DRAFT`、命名兼容和保留目录抽取行为，均符合所述裁决。

   第 2 条中，解码后 5 MiB 限制及错误处理满足；但仅检查 `Content-Length`，不能兑现“请求体超过 8 MiB 在解析前拦截”的完整承诺。解码后校验发生得太晚，无法限制此前接收、缓冲和 JSON 解析的资源消耗。

2. **§3 不算本片缺口，需要单独送审处理。**

   本片明确保持既有抽取语义，因此无需在本片修改解析器。但“同块同货号不同价只保留第一条”属于已知的数据正确性问题，应作为后续修复项记录。

   单独送审时应明确：完全重复如何去重、不同价格如何形成冲突候选，以及既有目录数据是否需要重新抽取。改动不宜直接简化为“所有重复都改成候选”。

   对外交付说明须明确这一限制；返回的 `warnings` 应能体现被忽略记录的 `unsupported` 计数，避免用户把“没有冲突待办”理解成“没有价格冲突”。

3. **对外交付前必须补：覆盖所有受支持传输方式的请求体硬上限。**

   可以在应用接收层累计实际字节并截断，也可以由不可绕过的入口层保证。要求是：**累计超过 8 MiB，即在完整缓冲和 JSON 解析前终止，返回 413 / `PAYLOAD_TOO_LARGE`**。`Content-Length` 检查可保留用于提前拒绝。

   补充验收证据至少覆盖：无 `Content-Length` 的超限请求、chunked 超限请求，以及拒绝后无数据库残留；声明长度与实际长度异常的请求，也不能绕过入口限制。

完成该硬上限补项后，可解除本片的对外交付条件；无需等待解析器后续片。
