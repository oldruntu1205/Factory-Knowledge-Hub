# L1 送审稿：词法查询构造（字级 AND）的修复方案

- 日期：2026-11-04
- 提出方：L2 实施
- 风险归类命中：**对外行为变化（检索返回集合）**、**契约条款边界（recall/精度承诺）**
- 请只做判断：**不要探索仓库、不要读源码、不要跑测试**。

## 1. 事实（已实测，2026-11-04）

语料：仓库 18 篇 Markdown / 181 个 child 切片；评测集 50 条中文问题（人工挑 needle + 所属文档）。
同一份数据、同一 ACL 主体、同一 scope，K=10：

| 召回方式 | recall@10（片段） | doc@10 | 平均耗时 |
|---|---|---|---|
| 现行词法（`plainto_tsquery`，**逐字 AND**） | **0.060**（3/50） | 0.060 | 1.8 ms |
| 词法 OR 变体（同一索引，仅把查询改成 `字 | 字 | …`） | **0.660**（33/50） | — | 同量级 |
| 混合（BGE-M3 + 词法 RRF） | 0.800（40/50） | 0.900（45/50） | 61 ms |

原因：`cjk-char-v1` 把每个汉字切成独立词项，`plainto_tsquery('simple', …)` 把这些字**全部 AND**。
自然语言问句（如「为什么不把 ACL 下推到 SQL 里做」）几乎不可能在一个切片里同时出现全部字 →
零命中。词法对自然语言问句基本不可用，这不是"语义能力差距"，是查询构造缺陷。

**已知代价**：OR 会把常见字（的/是/在）也纳入匹配，精度会下降；当前没有测精度（只有 recall）。
`ts_rank_cd` 能缓解排序，但不能保证"只返回相关内容"。

## 2. 候选方案（请选一个并给出断言要求）

- **A. OR + `ts_rank_cd` 排序**：改动最小（一行查询构造），召回 0.06→0.66。风险：精度下降，
  短查询/单字查询可能返回大量弱相关结果。
- **B. OR + 匹配度阈值**：在 A 之上加一个约束，例如要求命中不同字数量 ≥ N（或 `ts_rank_cd` ≥ 阈值），
  阈值需定参；召回/精度可调，但要引入一个"拍脑袋"的参数（与 RRF 的取舍类似）。
- **C. 双字 bigram 索引**（新迁移 + 回填 `lexeme`，查询按双字切分）：精度天然更好，
  但需要改 `cjk-char-v1` 的索引语义与回填，成本最高；且换分词器必须重建全部 `lexeme`。
- **D. 不修词法，改由混合模式提供召回**：默认模式改成 hybrid 或强制 opt-in 才能用。
  与我们已裁决的「默认 lexical、生产未授权 hybrid」冲突，且未修词法时纯词法部署仍然不可用。

## 3. 契约影响（需要裁决的部分）

1. `POST /v1/knowledge/search` 的 `results` 集合会变（词法模式下召回显著增加）。
   `scoring` 仍是 `lexical-v1` 还是需要新值（如 `lexical-v2`）？
2. 既有契约表述「空结果与『都无权限』不可区分」「max_results 是上限、不保证填满」是否仍然成立？
   （OR 之后"空结果"会变少，但语义不变。）
3. 是否要求同时提供精度指标（例如 top-10 中无关条数）作为验收证据？当前只有 recall。

- 不探索仓库、不写代码、不跑测试；一次调用回完 §2 选择 + §3 三项裁决 + 必须补的断言。
