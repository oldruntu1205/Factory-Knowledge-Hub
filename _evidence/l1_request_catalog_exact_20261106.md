# L1 送审稿：目录结构化通道（货号/价格精确查询）+ 问答路由

- 日期：2026-11-06
- 提出方：L2 实施
- 风险归类命中：**DB schema 与迁移**、**对外行为变化（问答新增确定性路径）**、**审计口径**
- 请只做判断：**不要探索仓库、不要读源码、不要跑测试**。

## 1. 实测证据（为什么必须做）

客户目录（85 页 / 76,854 字符 / 196 块，含 **1,281** 条「货号 → 规格/单价」行）上的评测：

| 指标 | 结果 |
|---|---|
| 检索 recall@10（30 条自动生成的货号查询） | 词法 **0/30**，混合 **2/30** |
| 切块情况 | 逐条核对：每条「货号+规格+单价」整行**完整存在于** 2 个块（parent+child）→ 不是切块问题，是**排序** |
| 端到端（qwen3:14b，10 条） | `ANSWERED` **0/10**；价格答对 3/10；**引用 0/10** |

原因很清楚：
- 按字 OR 的词法查询被「货/号/单/价」等高频字淹没，精确编号反而排不进 top-10；
- 14B 在报价表场景不输出 `[evidence_id]`，于是即便价格答对也按规则被降级为 `REFUSED`。

而 1,281 条货号→规格/单价是**确定性对应**，可机器校验，不需要模型。

## 2. 拟议实现（待判）

1. **迁移 `0014_catalog_items.sql`**：新表
   `catalog_items(item_id, tenant_id, version_id, chunk_id, code, spec, price, currency, locator, created_at)`
   - 复合外键指向 `knowledge_versions` / `knowledge_chunks`（同租户）；
   - 与既有业务表一致：`ENABLE + FORCE ROW LEVEL SECURITY` + `tenant_isolation` 策略；
   - 唯一键 `(tenant_id, version_id, code)`（同一版本内货号唯一）。
2. **入库抽取**：`domain == 'product_catalog'` 时，在**同一事务**内对已落库 child 块做行抽取
   （正则：`^([A-Z]{1,3}\d{5,8})\s+(.+?)\s+(\d{1,6}\.\d{2})$`），写入 `catalog_items`；
   抽取失败的行**不猜**，只保留原文，并在 `warnings` 里计数。
3. **查询服务**：`CatalogLookup.find(tenant, code)` —— 只返回**当前可检索版本**（`APPROVED_INTERNAL`/`PUBLISHED_PUBLIC`）且通过 ACL 复核的条目。
4. **问答路由**（`AnswerService`）：
   - 查询里恰好一个货号 → 精确通道，**不调用模型**，直接给出条目 + 来源定位；
   - 命中：`ANSWERED`，`citations` 指向该行的 chunk（`version_id`/`locator` 取系统侧）；
   - 未命中：`REFUSED/NO_EVIDENCE`，同样**不调用模型**；
   - 无货号 / 多个货号 → 走现有 RAG 链路不变。
5. **审计**：精确通道同样写 `rag_queries`（`model_id = 'catalog-exact:v1'`）+ `rag_citations`；query 仍只存 HMAC。
6. **可选 HTTP**：`GET /v1/catalog/items?code=`（权限沿用 `knowledge.search`），便于人工核对；
   若你不希望本切片扩契约，我就不加。

## 3. 待判问题

1. **抽取范围**：只对 `domain='product_catalog'` 抽取，还是对全部文档尝试？（我倾向只对该域，避免把普通文档里的数字误当价格。）
2. **路由规则**：唯一货号 + 未命中时，是直接 `REFUSED/NO_EVIDENCE`，还是**回退到 RAG** 再试一次？
   （我倾向不回退：回退会让"精确通道没命中"被 RAG 的模糊结果掩盖，且成本翻倍。）
3. **多货号查询**：一次问两个以上货号时怎么办？（我倾向：不路由，走 RAG，并在审计里标注未路由原因。）
4. **精确通道是否允许模型参与**（例如模型把问题改写成货号）？（我倾向不允许：可校验性优先。）
5. **版本失效语义**：条目随版本 `REVOKED`/`DISCARDED` 自动不可见（查询时 join 状态），还是迁移里级联删除？
   （我倾向 join 状态、不删数据——与"弃用/撤销只改状态"的既有纪律一致。）
6. **价格字段**：`numeric(12,2)` + `currency` 默认 `CNY`；是否需要保留原文价格串（防止千分位/区间价被格式化）？
   （我倾向同时存 `raw_text` 便于对账。）
7. **权限**：精确通道是否需要额外 scope（如 `knowledge.catalog.read`），还是沿用 `knowledge.answer` / `knowledge.search`？
8. **是否需要新增端点**（§2.6）？

## 4. 实施侧计划要补的断言（供裁决裁剪）

1. 迁移可重复应用；回滚脚本可安全回退（有数据时拒绝还是清表，待你定）；
2. 抽取：正常行 / 缺价格的说明行 / 区间价（如 `12.00-15.00`）/ 千分位 / 重复货号 各自行为明确；
3. 抽取不改变原文切片与检索行为（只新增结构）；
4. 精确通道命中：`ANSWERED` + 引用定位与原文一致 + `model_id='catalog-exact:v1'`；
5. 精确通道未命中：`REFUSED/NO_EVIDENCE`，且**生成器调用次数为 0**；
6. 版本撤销/弃用后，条目查不到（joins 状态）；
7. 跨租户查不到；ACL 变更后条目随之不可见；
8. 审计：一次精确问答恰好一条 `rag_queries` + 一条 `rag_citations`；
9. 现有 RAG 路径行为不变（无货号的查询仍走原链路，回归用例不改）；
10. RLS：新表与既有表一致的租户隔离（越权读写均失败）。
