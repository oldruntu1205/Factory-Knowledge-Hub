# L1 终审：查询侧货号识别按实例规则（`44e6749`）

- 日期：2026-11-08
- 背景：你此前判定"查询侧识别应单独立项，不能据正则替换宣称 EAN 查询已支持"；本片即该项。
- 风险归类：路由语义变化（哪些问题走目录精确通道）；无 schema / 迁移 / 鉴权变更。
- 请只做判断：**不要探索仓库、不要读源码、不要跑测试**。

## 1. 实现

| 环节 | 之前 | 现在 |
|---|---|---|
| 查询候选 | 固定正则 `[A-Za-z]{1,3}\d{5,8}` | **实例规则** `fullmatch`（`catalog_rules.code_pattern`）；读路径缺规则时用工厂正则兜底 |
| 数量歧义 | 无 | 前 10 字符含数量词（要/买/共/数量…），或紧邻「数字+单位」（`3 个 6901…`），或后面紧跟单位/金额词（`… 元`）→ 不当作货号 |
| 表格渲染 | 固定正则判定货号行 | 同一实例规则（`render_evidence(code_pattern=…)`），由 service 传入 |
| 判定条件 | 恰好一个货号 + 明确询价/询规格 | 不变（仍不抢答：无意图词仍交回 RAG） |

读路径**不加锁**、缺规则**不阻断**（已有目录照常作答）。

## 2. 验收（`tests/e2e/test_catalog_query_ean.py`，3 条，真实 PG + 业务角色 + HTTP）

1. 规则 `^\d{8,14}$` + EAN 目录 → 问「6901234567892 的规格是什么？」→ `ANSWERED`，
   `500ml` 在答案里，引用指向该版本；
2. 「这次要 3 个 6901234567892 的规格吗？」→ 审计 `route != catalog_exact`（没有被当成货号抢答）；
3. 工厂租户（未改规则）问 `A112420 的单价` → 仍 `ANSWERED` + `39.00`（回归）。

## 3. 已知边界（本片未做，如实说明）

- 判定仍是**规则 + 启发式**，不是完整的句法/意图解析：
  「6901234567892 的规格」在无单位词时会被当货号（即使它其实是订单号）；
- 规则由实例维护，若客户把规则写得过宽（如 `^\d+$`），查询侧误判概率上升——
  本片没有对"过宽规则"做风险提示；
- 数量语境排除是**中文词表 + 单位词**，不含英文单位（`pcs`, `carton`）。

## 5. 需要你判断的三点

1. 「无单位词但带号牌形态的长数字」是否一律当货号？我倾向**是**（用户既然贴了完整号牌，
   多半就是要问它），但会带来"订单号被当货号"的边界。
2. 是否需要给"过宽规则"加提示（例如 `^\d+$`、`.*` 在 PUT 时 warn 或拒绝）？
   本片没做，我认为属于运营风险提示而非正确性。
3. 英文单位（pcs/carton）是否要一并纳入数量语境排除？本片只做中文。
