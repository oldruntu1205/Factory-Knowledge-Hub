# L1 送审：10 万切片检索性能优化方案（目标 p50 ≤1s / p95 ≤2s，recall 不低于 0.62）

- 日期：2026-11-09
- 基准：`5d3e3be`（10 万切片 p50 2.71s / p95 3.63s；候选 1.32s + 统计 1.43s）
- 证据：`_evidence/retrieval_perf_20261109.md`
- 沙箱：`read-only`；**不要探索仓库**；只基于本文判断。
- 预算：本切片第 1 次 L1 调用。

## 一、事实

100k 合成切片、单查询、4 个 ACL：

| 项 | p50 |
|---|---:|
| 总检索 | 2.71s |
| 候选 SQL（`ts_rank_cd` 全排序取 200） | 1.32s |
| BM25 全范围统计（N/avg_len/df） | 1.43s |

进一步实测：
- 只算 `N/avg_len`、不取 `lexeme` 的基准统计：**94ms**（当前 `_STATS_SQL` 把它和逐词 df 混在一条 CTE，590ms）；
- 逐词 exact df（GIN count）：稀有词 24–38ms，高频词 90–140ms；
- 查询「冷凝管的规格和接口是多少」的 12 个字级 term 中，真正有判别力的只有 冷/凝/管（df/N≈0.167），
  其余（的/和/多/少/规/格/接/口/是）df/N≈1 或 0。

## 二、拟定方案（不改 schema）

### 1) 统计拆两段

- **Base**：只查 `acl_policy_id/policy_json/count(*)/sum(length(chunk_text))`，不取 `lexeme`（实测 94ms）；
- **Term df**：只对**选中的少数判别词**做 exact GIN count（每个 24–140ms）。

### 2) 判别词选择

- 先用 **1% `TABLESAMPLE SYSTEM`** 对可见范围抽样，估计每个 term 的 df；
- 丢弃估计 `df/N > 0.30` 的 term；
- 至少保留 1 个；若全部被丢，**回退到全部 term**（慢路径，但语义不丢）；
- 用选中 term 重构造候选查询（仍是 OR），候选 SQL 只扫少量命中；BM25 统计也只算选中 term。

### 3) 版本与回归

- 新 `scoring=lexical-v4`，保留 v3 作为历史/回退；审计枚举与契约同步；
- 冻结 50 条 recall 用例：**recall@10 不得低于 v3 的 0.62**；不达标就不启用；
- 性能门槛：10 万 p50 ≤1s、p95 ≤2s（单查询、非并发；SLO 来自本轮用户确认的建议目标）。

## 三、请 L1 判断

1. **抽样选词**是否可接受？1% `TABLESAMPLE SYSTEM` 的估计误差可能导致同一查询选词不稳定；
   是否应改为**精确统计表**（schema + refresh），还是允许抽样 + 回退？
2. **丢弃高频 term** 是否属于检索语义变更？是否必须保持 `scoring` 新版本、并禁用默认启用直到 recall 达标？
3. **回退条件**：全部 term 高频时回退全量（慢）是否合理？是否应直接返回低召回结果/人工？
4. **精确 df 的 GIN count** 与当前 `_STATS_SQL` 在“可见性 + ACL”口径上是否等价？需要注意哪些
   事务/RLS/索引代次细节？
5. **目标可达性**：按 94ms base + 3×~30ms df + ~300ms 候选，预计 0.5–0.8s；
   但 p95 可能受首个查询/抽样/缓存影响。是否接受这个不确定性，还是必须先做统计表？
6. 若 L1 认为抽样不可接受，请给出最小可批准的替代（统计表字段/刷新触发/失效语义）。
