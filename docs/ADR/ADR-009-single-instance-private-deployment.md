# 单实例私域部署（架构决策 ADR-009）

- 状态：**已确认**（2026-11-08，用户拍板）
- 影响范围：交付形态、部署边界、配置面；**不改变**核心检索/权限/引用/撤销逻辑

## 1. 决策

本产品是**可复用的 RAG 知识基座**，交付形态为：

| 项 | 决策 |
|---|---|
| 部署 | **单用户私域部署，一客户一套独立实例** |
| 复用 | 各客户复用**同一套代码与 Knowledge API** |
| 数据 | 每套实例**各自**管理资料、索引、凭据、配置、审计 |
| Agent | 每套实例可接入**多个 Agent**，按用途授权（scope + allowed_scopes） |
| 排除 | 多租户 SaaS、跨客户管理、计费 |
| 兼容 | 现有 `tenant_id` **保留**（单实例内仍用它做数据边界，未来若做 SaaS 不必重写） |
| 首个应用 | 工厂知识中枢 |

推论：**实例之间的隔离靠部署边界**（独立数据库、独立角色、独立 JWT 密钥、独立 index_generation），
不靠应用内多租户逻辑；应用内 `tenant_id` 仍必须正确，它是"一套实例内多用途/多 Agent"的边界。

## 2. 这与现有实现的关系

现有实现已经满足该形态，无需改核心代码：

- 认证：每实例独立 `FKH_JWT_SECRET`，A 的令牌在 B 上必然 401；
- 数据：每实例独立数据库；业务角色只在该库内被授权（跨库访问被 PG 拒绝）；
- 索引：`index_generation` / `index_visibility` 是**每库**的，互不影响；
- 撤销：`ReviewService.revoke` 只作用于本库；
- 审计：`rag_queries` / `evidence_access_log` / `outbox_deliveries` 均按实例库独立。

## 3. 需要**尽量**留在应用层的部分（本轮已识别）

这些不是"多租户 SaaS"，而是**行业/客户差异**，应当可配置而不是改内核：

| 类别 | 现状 | 建议 |
|---|---|---|
| 知识域枚举 | `knowledge_documents.domain` 的 CHECK + `VALID_DOMAINS` 硬编码工厂域 | 移到应用层配置（域清单表或配置文件），内核只存字符串 |
| 目录货号规则 | DB CHECK `^[A-Z]{1,3}[0-9]{5,8}$` | 按客户目录格式配置（正则 + 校验器） |
| 目录货币 | `currency IN ('CNY')` | 允许配置货币集合 |
| 商务承诺词表 | `_COMMITMENT_KEYWORDS` 中文外贸词 | 按客户业务配置（词表文件），并允许附加英文/行业词 |
| 演示语料/页面文案 | `_corpus/*`、`tools/demo_*` | 属演示资产，不进内核 |

本轮验收用 `bakery_equipment` 域试探，得到 **422**——这是当前**真实阻塞点**（见 `docs/DEPLOY-SINGLE-INSTANCE.md` §4）。

## 4. 验收方式

`tests/e2e/test_two_instances.py`（4 条）用两个独立数据库 + 独立业务角色 + 独立 JWT 密钥
模拟两套实例，验证：不同行业资料可用、凭据不跨界、撤销互不影响、域枚举阻塞被记录。

## 5. 非目标（明确排除）

- 跨实例统一登录、跨实例检索、集中计费；
- 多租户共享数据库（`tenant_id` 仍保留，但**不作为跨客户边界**）；
- 实例间数据同步（各客户自行管理）。
