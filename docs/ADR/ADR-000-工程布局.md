# ADR-000：工程布局采用单包多模块

- **状态**：ACCEPTED（2026-11-03，待业务方复核）
- **决策范围**：仓库代码组织方式
- **相关**：L1 §10 建议结构

## 背景

L1 §10 给出了 `apps/` + `packages/` 的多包结构，每个服务与共享包各自独立（api、worker-ingestion、mcp-server、authz、retrieval 等）。
这种结构在服务边界稳定、需要独立发布镜像时是正确的。当前项目处于 Phase 0，服务边界仍在演进，
检索、治理、培训三条链路的共用代码比例很高。

## 决策

Phase 0 采用 **单包多模块**：

```text
src/fkh/{api,authz,domain,retrieval,gateway,observability,workers,mcp}
```

- 所有服务共用一份 `uv.lock` 与一套测试配置；
- 各服务通过不同 entrypoint（uvicorn / worker 进程）区分，而不是不同包；
- `contracts/` 独立于代码，作为契约单一来源。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 单包多模块 | 重构成本低、依赖统一、CI 简单 | 模块间可互相 import，边界靠约定维持 | 采纳 |
| uv workspace 多包 | 强边界、可独立发布 | 跨包改动需同步多份版本，Phase 0 收益不抵成本 | 暂缓 |
| 单体不分模块 | 最省事 | 无法承载 L1 的服务划分与权限边界 | 否决 |

## 后果

- 正面：Phase 0–2 迭代快；测试与迁移只需一套环境。
- 负面：模块边界缺少编译期约束。缓解措施是在 `src/fkh/<module>/__init__.py` 中显式导出公共接口，
  并禁止跨模块直接引用内部实现；`mypy --strict` 与 code review 共同承担边界审查。
- 拆分时机：当某服务需要独立伸缩、独立发布镜像，或出现跨团队并行开发时，把该模块提升为独立包。
  触发条件写入 Phase 3 评估项。
