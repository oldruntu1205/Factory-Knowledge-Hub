# 解析与切片规格

对应 L1 §4.1–§4.3。本文记录实现取舍、已知限制与实测数据，供后续阶段复核。

## 1. 范围

已实现：Markdown、CSV/TSV、HTML、DOCX、可提取文本的 PDF 的解析，以及父子切片。

未实现：
- 扫描件 OCR。OCR 引擎与语言由 ADR-05 决定，在此之前扫描页只标记为需要复核，不做静默降级。
- Embedding 与索引写入。Embedding 模型由 ADR-04/06 决定。
- 旧版 `.doc`、`.xlsx`。前者需 LibreOffice 转换，后者要求导出为 CSV，属独立处理链路。

## 2. 解析器选型

| 格式 | 实现 | 许可 | 理由 |
|---|---|---|---|
| PDF | pdfplumber | MIT | 需要原文坐标与表格结构 |
| DOCX | python-docx | MIT | 能按文档顺序同时给出段落与表格 |
| HTML | beautifulsoup4 + lxml | MIT / BSD | 需剔除脚本样式、识别合并单元格 |
| Markdown | markdown-it-py | MIT | CommonMark 兼容，表格可开启 |
| CSV | 标准库 csv | PSF | 多编码（UTF-8/GB18030）自动识别 |

**PDF 不用 PyMuPDF**：它是 AGPL-3.0。本项目面向制造业客户做闭源交付，AGPL 的传染性
会让整个交付物的许可状态变复杂。pdfplumber 在 MIT 下能提供坐标与表格，性能较低但可接受。

## 3. 必须人工复核的情形

`ReviewReason` 是一个封闭枚举。出现任意一项，文档不得直接进入发布索引：

| 原因 | 触发条件 | 为什么必须人工看 |
|---|---|---|
| `LOW_OCR_CONFIDENCE` | OCR 通道启用后置信度低于阈值 | 推断出来的规格值不能当事实 |
| `CROSS_PAGE_TABLE` | 相邻两页表头相同，疑为同一表被分页切断 | 跨页表的行归属容易错位 |
| `MISSING_UNIT` | 数值列无单位线索 | mm 与 cm 混淆是玻璃仪器最常见的错误 |
| `TABLE_STRUCTURE_UNCERTAIN` | 表头缺失、列数不齐、合并单元格 | 列错位后的规格表比没有表更危险 |
| `EMPTY_DOCUMENT` | 无任何可索引块 | 防止空壳文档进入索引后被引用 |
| `HEADING_HEURISTIC` | PDF 标题由字号推断 | 推断出的层级不是原文结构 |
| `PARSER_FALLBACK` | 页面无可提取文本（疑似扫描件） | 需要 OCR，当前未启用 |

## 4. 切片策略

### 4.1 为什么按 token 而不是字符

字符数与 token 数在中文技术文档里偏差很大。按字符切会把「24/29 接口」这类短行切断，
或把整张参数表塞进一个 child。

当前 token 计数是**近似**（`approx-cjk-v1`）：CJK 1 token/字、拉丁词 1.4 token/词、
其余符号 0.4 token/个。Embedding 模型确定后必须换成真实 tokenizer 并更新 `tokenizer_id`，
否则同一文档在不同模型下会产生不同切片，引用位置无法复现。

### 4.2 分组层级

`section_break_level` 默认 2：一级、二级标题切断 parent，三级以下只影响 child 的
`heading_path`。

这个选择来自实测。若按所有标题切分，契约类文档（小节密集）会产生大量百 token 级碎片。
在仓库内 40KB 中文契约文档上的对比：

| 策略 | parent 数 | parent token 中位数 | child token 中位数 |
|---|---|---|---|
| 按全部标题切分 | 59 | 132 | 138 |
| 按一二级标题切分（当前） | 17 | 502 | 344 |

第二种策略下 child 中位数落进 L1 的 250–450 区间，且没有任何 parent 超过 1500。

### 4.3 仍然低于下限的 parent

同一份文档里仍有 76% 的 parent 低于 800 token。原因不是算法：这份契约按二级标题分节，
部分小节本身就只有一二百字。跨节合并能把数字做得好看，但会把无关章节塞进同一上下文，
损害引用准确性。

因此保留短 parent，只产出 warning 供人工抽查。若要更长的父块，应调整
`section_break_level` 或 `parent_min_tokens`，而不是在代码里隐式合并。

### 4.4 表格

- 小表整表成块，表头与单位保留在首行。
- 大表按行拆，**每行重复表头与单位**。单行数据「29/32 | 400」脱离列名后无法判断含义。
- 合并单元格一律标记 `TABLE_STRUCTURE_UNCERTAIN`。

## 5. 已知限制

1. PDF 标题识别基于字号，同一文档内字号不统一时会误判，已标记 `HEADING_HEURISTIC`。
2. PDF 表格依赖线框；无框表格会退化为文本行，列关系丢失。
3. DOCX 合并单元格通过底层 `tc` 去重检测，跨行合并只能发现存在、无法还原结构。
4. HTML 只读取顶层块元素，深层嵌套布局（如卡片式 div 排版）会被压平。
5. CSV 无表头检测是启发式，命中的是「每格都有数字且无表头关键词」，可能漏判。
6. 文本长度按字符计（`text_length`），与 token 不同，不要混用。

## 6. 复核要求

ADR-04/06 签署后：
- 用真实 tokenizer 替换近似计数器，重跑切片并对比分布；
- 用真实产品目录校准表格解析，确认无框表与跨页表的处理方式；
- 把 `MISSING_UNIT` 的检测阈值写进固定规则并加入回归集。
