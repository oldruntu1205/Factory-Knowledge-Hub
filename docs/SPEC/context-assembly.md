# 上下文组装规格

对应 L1 §4.4-5、§8.4。位置在「检索命中」与「生成回答」之间。

## 1. 为什么需要这一层

检索返回的是 child（250–450 token 的片段），但生成时需要更完整的上下文。
朴素做法是命中的 child 一律回溯到 parent 全文——这会直接击穿权限：

> parent 的文本包含它下面**所有** child 的内容。检索只命中了其中一条，
> 但恢复出来的整段里可能还有另一条对当前主体不可见的句子。

L1 §8.4 把这条列为 P0：parent 混合了可公开与内部段落时，不能因公开 child 命中就恢复整个 parent。

## 2. 规则

`assemble_context()` 对每个命中：

1. 命中项自身必须通过 ACL；
2. 若有父块，且**该父块下全部 child** 都通过 ACL、父块自身也通过 → 恢复父块全文；
3. 否则只用命中 child 的原文，不做任何扩展；
4. 缺策略、策略 JSON 结构损坏，一律视为不可见（与 `authz.policy` 同口径）。

判定本身复用 `authz.parent.plan_restore`，本层只负责取数、去重与预算。

**必须取回完整子块清单。** 只查命中的那些 child 无法证明整体可恢复——未命中的兄弟块同样在 parent 文本里。

## 3. 去重与预算

- 同一父块被多条命中指向时只出一块（父块已含全部内容）；
- 同一父块下**不同** child 各自命中时分别成块，不合并——它们是不同段落；
- `max_blocks`（默认 8）与 `max_tokens`（默认 6000）双限，超出计入 `dropped`；
- 被 ACL 拒绝的计入 `denied`，与预算丢弃分开统计——两者原因不同，混在一起会让排障误判。

## 4. 接线时机

当前**尚未接入 HTTP**。`/v1/knowledge/search` 只返回片段级候选，组装发生在问答阶段
（`POST /v1/knowledge/answer`），而问答链路依赖 ADR-04/06 的模型选型。

这条不是遗漏，是分层：检索端点给的是"候选"，上下文是针对某次生成任务定制的，
两者预算与去重策略不同，不应该压成一个接口。

接入时的要求：
- 组装结果必须带 `from_parent` 标志，便于审计时区分"用了整段"还是"只用了片段"；
- `parent_restores` 数要进检索审计，异常升高通常意味着 ACL 配置变宽了。

## 5. 与证据端点的一致性

`GET /v1/evidence/{id}` 与这里是同一套 ACL 规则的两个入口，判定口径必须一致：
同一主体对同一 chunk，两处结论不能不同。改动任何一侧都要同步另一侧，
否则会出现"检索能用、取证被拒"或反过来的矛盾。

## 6. 验收证据

`tests/e2e/test_context_assembly.py`（8 项）：

| 用例 | 断言 |
|---|---|
| 父块及其全部子块可见 | 恢复父块全文 |
| 兄弟块仅管理层可见 | 退回 child 原文，敏感内容不出现 |
| 同一父块多条命中 | 只出一块 |
| 无父块的独立片段 | 原样返回 |
| 主体无权限 | 零块，计入 denied |
| 策略 JSON 损坏 | 视为缺失，拒绝 |
| 超出块数预算 | 截断并计入 dropped |
| 空命中 | 空结果且不计 denied |
