# Embedding 选型与混合检索

对应 L1 §4.4、ADR-04/06。记录选型依据、当前实现状态与切换流程。

## 1. 结论

| 项 | 决策 | 依据 |
|---|---|---|
| 模型 | **BGE-M3**（`BAAI/bge-m3`，1024 维，MIT） | 与 0002 已定的 `vector(1024)` 一致；中文强；同时输出 sparse |
| 部署 | 本地权重，推理全程离线 | **数据不出境**（用户 2026-11-04 确认） |
| 设备 | CPU 起步，GPU 到位后切换 | 同一模型、同一维度，**换设备不需要重建索引** |

选 BGE-M3 的主要理由不是榜单分数，是它同时产出 sparse 词权重：可以直接替换当前的
字级倒排（`cjk-char-v1`），一个模型解决稠密召回与稀疏召回两件事，不必再引 zhparser。

## 2. 为什么排除境外 API

用户明确"数据不出境"。要索引的是 C1–C3（产品技术参数、工艺诀窍），一旦送出境：

- 合规上，等于把知识库的边界交出去，ADR-04 也就没有讨论余地；
- 工程上，检索链路会多一个外部依赖，断网即不可用，与"私域部署"的定位冲突。

因此实现里**不提供任何远程 endpoint 配置项**，也不写任何 HTTP 调用路径。
权重从本地缓存加载（`SentenceTransformer` 首次使用后即离线）。

## 3. 许可证检查（容易踩的坑）

| 模型 | 许可 | 可否商用 |
|---|---|---|
| BGE-M3 / bge-large-zh | MIT | 可 |
| Qwen3-Embedding | Apache-2.0 | 可 |
| **jina-embeddings-v3** | **CC BY-NC-4.0** | **不可** |

榜单排名靠前的模型里有非商用许可，选型时必须看 license，不能只看 MTEB 分数。

## 4. CPU 与 GPU 的差别

- **查询**：单条编码，CPU 在百毫秒级，交互可接受；
- **全量索引**：CPU 明显慢（每千条数分钟），但这是一次性离线任务，可放夜间；
- **切换 GPU**：只改 `FKH_EMBEDDING_DEVICE=cuda`。模型 ID 与维度不变，向量空间一致，
  已有索引继续有效——这是选"同模型换设备"而不是"换小模型"的核心原因。

## 5. 维度与换模型的代价

`knowledge_chunks.embedding` 已固定为 `vector(1024)`。换到不同维度的模型必须走列迁移：

1. 新增 `embedding_v2 vector(N)` 与索引；
2. 双写并灰度；
3. 回填完成后切换读取列；
4. 删除旧列。

不能直接改列类型——已有向量无法自动转换，且会让"新旧向量混在同一列"这种最难排查的
状态出现在生产里。检索侧已按 `embedding_model_id` 隔离，旧模型向量不会被新模型召回
（`test_vector_from_other_model_is_ignored` 固定了这条）。

## 6. 验收前必须做的实测

榜单第一不等于在你的语料上第一。玻璃仪器术语（磨口 24/29、回流提取、硼硅 3.3）
在通用语料里出现频率低，模型表现差异会比榜单大。

做法：从客户真实资料挑 50–100 条问题，人工标注正确片段，测 recall@10。
低于词法基线就说明这个模型当前不值得引入。

> 2026-11-04 已用**仓库工程文档**（19 篇 / 190+ 个 child）与 50 条人工题做过两次：
> 词法（AND）0.06 → 词法（OR，`lexical-v2`）0.68 → 混合 0.84（CPU 17ms / 83ms 每查询）。
> 完整口径、精度、偏置说明与复现命令见 [`recall-benchmark.md`](./recall-benchmark.md)。
> **客户语料验收仍未做**，该数字只支持相对比较。客户语料提交格式、校验脚本与验收下限见
> [`customer-recall-intake.md`](./customer-recall-intake.md)。

链路用 `DeterministicTestEmbedder`（哈希伪向量）验证过：它没有语义能力，
但足以证明**写入、隔离、双路召回、融合去重、融合后鉴权、模式上报与审计一致**这些工程环节是通的。
生产环境会**拒绝** `test` provider（`build_embedder` 按 `FKH_ENV` 校验），避免伪向量污染验收结论。

真实模型接入只需：`uv sync --extra embedding` → `FKH_EMBEDDING_PROVIDER=bge-m3`
→ `FKH_RETRIEVAL_MODE=hybrid` → 重新入库（或在已有数据上跑一次回填）。
接线与契约变更的落实见 `docs/SPEC/retrieval-lexical.md` §9–§10。

## 8. 混合检索的两个设计点

**为什么用 RRF 而不是加权分数。** 向量相似度在 0–1，`ts_rank_cd` 无上界，
两者相加必须各配一个归一化参数，而这个参数只能靠调。RRF 只用排名，
天然不受量纲影响，也不需要在试点阶段引入一个拍脑袋的权重。

**融合之后仍要鉴权。** 向量召回在 SQL 里只做了租户、范围、状态三种过滤，
细粒度 ACL（JSONB 策略）在应用层判定。若融合后不做这一步，就是"先召回后鉴权"——
越权内容已经进入候选集，后面再拦也只是补救。
