# 部署硬件与换机指引

面向交付：给出可选配置、换设备的风险边界与验证方法。结论先行——**GPU 是加速件，
不是方案的组成部分**。CPU 已能跑通全链路，加卡只影响索引耗时。

## 1. 三层配置

| 配置 | 硬件 | 索引 10 万切片 | 查询延迟 | 适用 |
|---|---|---|---|---|
| 最低配 | 8 核 / 16 GB / 无 GPU | 2–5 小时（夜间） | 100–300 ms | 文档量小、隔天生效可接受 |
| 推荐配 | + RTX 3060 12G 或 T4 16G | 3–6 分钟 | 10–20 ms | 日常增量入库 |
| 完整配 | + 24 GB 显存（3090 / L4 / A10） | 3–6 分钟 | 10–20 ms | 同时跑本地 LLM（4-bit 7B 约 5 GB） |

存储与内存另算：10 万切片向量约 400 MB，HNSW 索引再加 1.5–2 倍；PostgreSQL 建议
独立盘，内存 ≥ 8 GB 用于共享缓冲。

## 2. 3060 12G 够不够

够。BGE-M3 约 5.7 亿参数，fp16 显存占用 2.5–3 GB（batch 16），12 GB 用不满。
余下空间还能挂一个 4-bit 量化的 7B 生成模型，也就是"嵌入 + 生成"一张卡。

但有三条现实约束，交付时要讲清楚：

1. **消费卡不是为 7×24 设计的**。无 ECC 显存，风扇是消费级。长期满载故障率高于
   服务器卡。客户能接受就写进运维约定，不能接受就换 T4/A2000。
2. **二手 3060 是矿卡重灾区**。若客户自行采购，给出验机标准（GPU-Z 查看显存颗粒
   与 BIOS、FurMark 30 分钟温度与功耗曲线、跑一次完整索引看有无 ECC 类错误导致的
   结果异常）。
3. **客户机房可能装不了**。非标设备入机房受限、无独显服务器、或本身是租用云主机。
   这种情况直接降到最低配，功能不受影响。

## 3. 换设备要不要重建索引

**不需要。** 向量由模型权重决定，与设备无关。同一份 BGE-M3 权重在 3060 与 T4 上
编码同一句话，余弦相似度在 0.9999 量级，排序一致。

唯一的边界是**精度差异**：CPU（fp32）与 GPU（fp16）的浮点累加顺序不同，向量会有
1e-3 级差异。这个差异通常不影响检索结果，但不是数学等价。

因此换机流程是：换之前跑一次自检，过了就直接用，不过就在新环境重跑索引。

## 4. 换机自检

```bash
# 准备 20–50 条真实文本，每行一条
uv run python -m fkh.tools.embedding_parity --texts samples.txt \
    --a-provider bge-m3 --a-device cuda \
    --b-provider bge-m3 --b-device cpu
```

输出三项：同文本余弦均值/最小值、top-10 排序重叠率。判定：

| 结果 | 含义 | 动作 |
|---|---|---|
| 余弦 ≥ 0.999 且重叠 ≥ 0.95 | 排序等价 | 直接混用，不重建 |
| 只过一项 | 有偏差 | 在新环境重跑索引 |
| 都不过 | 差异显著 | 不要混用，必须重建 |

维度不同会直接报错退出——那种情况没有混用可能。

## 5. 交付建议

**不要把显卡写进合同。** 写进去等于把交付风险绑在客户的硬件采购上：采购延期、
型号变更、机房不让装，都会变成你的问题。

推荐写法：把上表作为"建议配置"附件，主合同只承诺功能与性能指标（如"10 万切片
索引在 24 小时内可用"），硬件达标与否由客户决定。
